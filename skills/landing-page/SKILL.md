# 랜딩페이지 (Landing Page)

이 스킬로 만드는 랜딩페이지는 홍보물이 아니라 **가설 검증 도구**다.
창업자는 이 페이지 링크를 고객이 될 만한 사람 10명쯤에게 보내고, 몇 명이 버튼을 눌러 신청했는지 센다.
그래서 예쁜 것보다 세 가지가 먼저다. 5초 안에 뭘 파는지 알 수 있는가, 가격이 보이는가, 누를 버튼이 하나인가.
가격을 숨기거나 버튼이 여러 개면 신청 수가 나와도 무엇을 확인했는지 알 수 없다.

이 스킬은 **기획까지만** 한다. HTML·코드·디자인 시안은 만들지 않는다. 화면은 나중에 이 기획서를 넘겨 따로 만든다.
그래서 기획서는 만드는 사람이 되묻지 않아도 될 만큼 문구와 순서가 확정돼 있어야 한다. 사용자가 이 대화에서 코드를 직접 달라고 하면 그때 만든다.

읽는 사람은 대부분 예비·초기 창업자다. 디자인·개발 용어 없이 쓴다.

## 1. 입력 확인

대화에 market-diagnosis 리포트가 있으면 아래를 찾아 그대로 이어받는다. 두 결과가 서로 다른 가격이나 기준을 말하면 창업자가 무엇을 시험할지 헷갈리기 때문이다.

- `## 검증할 가설`의 가설 문장과 `검증 기준`(분모 / 신호 / 기준)
- `### 검증 재료`(헤드라인, 문제, 대체재와 비교, 가격, 믿을 이유, 신청 버튼 문구)
- `## 가장 약한 고리`, `고객 구조`(쓰는 사람·돈 내는 사람), `나중에 시험할 가격`, `위험 확인 뒤 시험할 것`
- `추정`, `가정`, `예시 기준`, `진단을 위해 고른 예시` 표시

리포트가 없으면 "누가 / 어떤 문제를 / 무엇으로 해결"과 가격을 짧게 묻는다. 대답을 받을 수 없으면 가장 그럴듯하게 정하고 `가정:`으로 표시한 뒤 진행한다.
경쟁사·가격 근거가 하나도 없으면 market-diagnosis로 먼저 진단하면 문구가 더 단단해진다고 한 줄 권한다.

**문구는 리포트에 있는 사실에서만 가져온다.** 후기, 고객 수, 만족도, 수상 이력, 전문가 추천을 지어내지 않는다.
없는 증거는 `[기존 고객 후기 1줄]`, `[만든 사람 이름 · 한 줄 경력]`처럼 창업자가 채울 빈칸으로 둔다.
가짜 증거로 받은 신청은 수요가 아니라 문구에 속은 숫자라서, 검증 도구로서 쓸모가 없어진다.

## 2. 어떤 페이지를 만들지 고르기

리포트 모양에 따라 페이지 종류를 하나 고르고, 맨 위에 어떤 경우인지 한 줄로 적는다.

**A. 재료가 다 있는 경우** — 검증 재료를 섹션에 그대로 옮긴다.
헤드라인 ← 오퍼, 문제 ← 시장, 비교 ← 대체재, 가격 ← 가격, 믿을 이유 ← 판매(걱정과 답), 버튼.

**B. '고를 이유가 아직 없음'** (헤드라인·비교가 "1단계 결과로 채움") — **불편 확인 페이지**로 기획한다.
진단이 차별점을 일부러 비워 둔 것이다. 여기서 차별점을 지어내 헤드라인에 쓰면 진단이 막아 둔 실수를 그대로 하게 된다.
- 헤드라인은 차별점 대신 **문제**(검증 재료의 '문제' 칸, 근거 있음)를 고객이 겪는 장면이나 질문으로 쓴다. 예: "온라인으로 산 향수, 생각한 향과 달랐던 적 있나요?"
- 비교 섹션 자리에 "이런 불편, 있으셨나요?"를 두고 리포트의 [남는 불편] 후보와 `진단을 위해 고른 예시`를 2~3개 나열한다. 리포트에 후보가 하나뿐이면 하나만 쓰고, 새 후보를 지어 넣지 않는다.
- 신청 폼에 "이 중 가장 불편했던 것"(객관식 + 기타)을 넣는다. 그러면 10명에게 보내는 일이 진단의 1단계(불편 확인)와 2단계(가격 확인)를 한 번에 한다.
- 가격은 리포트의 2단계 가격을 그대로 보여 준다.

**C. 가장 약한 고리가 위험** (검증 재료 대신 전문가 질문이 있음) — **대기 신청 페이지**로 기획한다.
- 결제·예약금을 받지 않고 "출시 알림 받기"처럼 대기 신청만 받는다. 허용되지 않는 사업이면 돈을 돌려줘야 하는 일이 생기기 때문이다.
- 리포트가 문제 삼은 표현과 방식은 페이지에 쓰지 않는다(예: 효능·치료·재활 표현, '최저가'·'합리적인 가격' 같은 염가 표방, 허가가 필요한 업무를 직접 해 준다는 문장). 무엇을 뺐는지 기획에 적는다.
- 가격은 `나중에 시험할 가격`을 "예정 가격"으로 보여 주고, 신호·기준은 `위험 확인 뒤 시험할 것`을 쓴다.
- 페이지와 별개로 **오늘 할 1가지는 리포트의 전문가 확인 그대로**라고 맨 끝에 적는다. 페이지는 확인을 기다리는 동안 수요를 보는 용도다.

**D. 기업·학교·기관이 돈을 내는 경우** — **한 장 소개서 페이지**로 기획한다.
- 버튼은 사전 신청 대신 리포트의 신호에 맞춘다: 데모 받아보기, 견적 요청, 파일럿 신청, 미팅 잡기.
- 담당자가 윗선에 넘길 수 있게 가격, 도입 절차, 계약 전 확인할 수 있는 것을 분명히 쓴다.
- 10명에게 보내는 방법은 단톡방보다 담당자에게 직접 보내는 첫 연락 메시지다. 리포트에 메시지 예시가 있으면 그것을 쓴다.

**E. 같은 시간에 사람이 모여야 하는 서비스** (가장 약한 고리가 성립 조건) — **참가 신청 페이지**로 기획한다.
날짜·시간·장소(또는 '각자 동네에서')를 헤드라인 가까이에 크게 쓰고, 버튼은 그 회차 신청이다. 기준은 신청 수가 아니라 실제로 나타난 비율이라고 적는다.

**F. 짧은 리포트**(확인 질문으로 끝남)이거나 판단 보류가 많아 가설이 없는 경우 — 페이지를 바로 만들지 않는다.
대화 상대가 창업자 본인이면 리포트의 확인 질문 중 페이지에 꼭 필요한 것(무엇을 파는지, 누구에게, 얼마에) 3개 이하를 묻고, 답을 받으면 A~E 중 하나로 기획한다.
답을 받을 수 없으면 해석 하나를 골라 `가정:`으로 표시하고 기획한다. 이 경우 신청 수가 그 해석이 맞는지까지 알려 주지는 않는다고 한 줄 적는다.

이미 운영 중인 상품이고 리포트가 실제 전환(문의→계약, 무료→유료)을 기준으로 정했으면, 페이지 버튼을 그 행동(문의하기, 오픈채팅 등)으로 맞추고 기준도 리포트 것을 쓴다.

## 3. 버튼과 신청 받는 곳

페이지만으로는 누가 신청했는지 남지 않는다. 그래서 버튼은 창업자가 결과를 볼 수 있는 곳으로 연결하도록 기획한다.
- 기본: 구글 폼·네이버 폼 같은 신청 폼 링크. 창업자가 링크를 주지 않았으면 `[신청 폼 링크]`로 두고, 폼에 넣을 질문을 함께 적는다.
- 리포트의 행동이 오픈채팅·예약·데모 요청이면 그 링크로 연결한다.
- 폼 질문은 3~5개: 연락처(이메일 또는 전화 중 하나), 지금 이 문제를 어떻게 해결하고 있는지, (B면) 가장 불편했던 것, (가격 확인이면) 이 가격이면 쓸지. 이름·연락처 외의 개인정보는 묻지 않는다.

버튼은 하나의 행동만 둔다. 같은 버튼을 위·아래에 반복하거나 모바일 하단에 고정하는 것은 괜찮다. "더 알아보기", "문의하기" 같은 두 번째 행동은 넣지 않는다.

## 4. 화면 구성 정하기

코드 대신, 나중에 화면을 만들 사람이 그대로 따라 할 수 있게 구성을 글로 정한다.
- 모바일 화면을 기준으로 첫 화면(스크롤 전)에 무엇이 들어가는지 정한다: 헤드라인, 한 줄 설명, 가격 또는 가격 위치, 버튼.
- 섹션 순서: 헤드라인 → 문제 → 비교(B는 불편 후보) → 가격 → 믿을 이유 → 버튼. 경우에 맞게 이름만 바꾼다.
- 이모지, 과장된 표현("혁신적인", "압도적", "최고의"), 근거 없는 숫자는 쓰지 않는다.
- 사진이 필요한 자리는 "[제품 사진: 무엇을 보여 줄지]"로 적는다. 남의 사이트 사진·로고·문장을 가져오지 않는다.
- 색·글꼴·레이아웃 같은 디자인은 정하지 않는다. 화면을 만들 때 정한다.

## 출력 형식

```
# [아이템명] 랜딩페이지 기획

페이지 종류: A 재료 그대로 / B 불편 확인 / C 대기 신청 / D 한 장 소개서 / E 참가 신청
(가정이 있으면) 가정: ...

## 이 페이지로 확인할 것
가설: "리포트의 가설 문장"
기준: 분모 ___ / 신호 ___ / 기준 ___ (리포트 그대로. 10명에게 보내면 분모는 보낸 사람 수)

## 섹션별 문구
| 섹션 | 문구 | 가져온 곳 |
(가져온 곳: 리포트의 어느 칸인지, 또는 "창업자가 채움")
(C면) 뺀 표현: ...

## 첫 화면에 보일 내용 (모바일, 스크롤 전)
1. 헤드라인 / 2. 한 줄 설명 / 3. 가격 / 4. 버튼 (같은 버튼을 어디에 반복하는지도)

## 신청 폼에 넣을 질문
1. ...

## 만들기 전에
- 5초 점검: 첫 화면에 보일 내용만 보고 뭘 파는지 / 가격이 보이는지 / 버튼이 하나인지
- 채울 빈칸: [신청 폼 링크], ...
- 10명에게 보낼 메시지: "..." (리포트 채널에 맞춰 한두 문장, 과장 없이)
- 결과 적기: 보낸 사람 수 ___ / 신청 수 ___ / (B면) 가장 많이 고른 불편 ___
(C면) 오늘 할 1가지는 여전히 리포트의 전문가 확인입니다: ...
```

기획서 맨 끝에는 화면을 만들 때 쓸 요청문을 아래 형식 그대로 붙인다. 창업자는 Claude Code에서 이 요청문 아래에 기획서 전체를 붙여 넣는다.

````
## 화면 만들 때 (Claude Code에 붙여 넣기)
```
이 폴더에 AXHub로 배포할 랜딩페이지 앱을 새로 만들어줘.
아래 기획서대로 화면을 만들고, 먼저 내 컴퓨터에서 띄워서 보여줘.
배포는 내가 말할 때 해줘.
- 버튼 링크: [신청 폼 링크, 없으면 빈칸]
- 모바일에서 먼저 보기 좋게
```
그다음 줄에 이 기획서 전체를 붙여 넣으세요.
````

답에 HTML·코드를 넣지 않는다. 이 기획서는 나중에 화면을 만들 때 그대로 붙여 넣는 입력이다.
고칠 때는 사용자가 말한 것 하나만 바꾸고, 나머지 문구·가격·버튼은 그대로 둔다. 가격이나 버튼을 바꾸면 검증 기준이 달라지므로 그 사실을 한 줄 알린다.
